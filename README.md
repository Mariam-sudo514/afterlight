# AFTERLIGHT — журнал RU/EN

Обычный Next.js App Router + TypeScript, локальный Supabase (PostgreSQL, Auth, private Storage) через Docker. Приложение работает с настоящей базой и серверными сессиями. `.openai/hosting.json`, Vinext и Cloudflare для запуска не нужны.

Облачный Supabase и Vercel настраиваются отдельно: **[пошаговое развёртывание](docs/DEPLOYMENT.md)**. Для облака используются `.env.cloud.local` и `work/cloud-deployment`; обычный `pnpm dev` продолжает читать локальный `.env.local`.

Текущий дизайн, мобильные карточки редактора и архивные метки `A / 02`, `A / 03` сохранены. Старая платформенная конфигурация, миграции SQLite и лицензии оставлены как справочные материалы в `legacy/cloudflare/`; приложение их не импортирует. Копия исходников перед переносом: `work/backups/before-next-migration.tar.gz` (локальная, исключена из Git).

## Требования

- Node.js **22.13+ внутри ветки 22.x**. Та же ветка закреплена для Vercel.
- pnpm **11.25.0** из `packageManager`.
- Запущенный Docker Desktop с доступом к Docker Engine; интернет нужен для первой загрузки пакетов и контейнеров.
- Свободный порт **3300** для сайта. Порт 3000 оставлен другим проектам.
- Свободные порты **55430–55436, 55439** для основного Supabase. Проверки используют **3400** и **56430–56436, 56439**.

Команды не останавливают чужие контейнеры, не удаляют volumes и не используют `supabase stop --all`, `--no-backup` или `db reset`. Проекты Docker: `afterlight-local` и отдельный `afterlight-test`. Для обоих создаются свои сети с привязкой опубликованных портов только к `127.0.0.1`.

В текущем Docker Desktop одной настройки сети оказалось недостаточно. Поэтому команда запуска временно использует приватный Unix-сокет (`scripts/docker-loopback.mjs`), который задаёт явный `HostIp=127.0.0.1` только при создании контейнеров с меткой текущего проекта AFTERLIGHT. После запуска проверяется фактическая привязка портов. Глобальные настройки Docker не меняются; дополнительный сетевой порт не открывается.

## Первый запуск

В обычном терминале:

```bash
cd /Users/maria/Desktop/afterlight
pnpm install --frozen-lockfile
pnpm local:start
pnpm local:owner
pnpm dev
```

`local:start` запускает сервисы, применяет только новые миграции, записывает локальные ключи в `.env.local` с правами `0600` и выполняет seed. Ключи не выводятся в отчёт команды. Если `.env.local` указывает на другой Supabase, команда откажется перезаписывать его.

`local:owner` запрашивает email, имя и пароль **в терминале**. Пароль вводится без отображения дважды; минимум 12 символов, максимум 72 байта UTF-8. Пароли не передаются аргументом, через переменную окружения или чат и не сохраняются в файлах проекта. Команда создаёт подтверждённого пользователя Auth и явно назначает его UUID владельцем. Существующего владельца она не заменяет. Публичная регистрация выключена.

До выполнения `local:owner` журнал доступен для чтения, но права редактора не получает никто. Владелец не создаётся при первом посещении сайта.

Адреса:

- Журнал RU: **http://127.0.0.1:3300/ru**
- Журнал EN: **http://127.0.0.1:3300/en**
- Вход: **http://127.0.0.1:3300/login?lang=ru**
- Редактор: **http://127.0.0.1:3300/admin?lang=ru**
- Локальная панель Supabase: **http://127.0.0.1:55433**
- Локальный просмотр писем: **http://127.0.0.1:55434**

Используйте один и тот же hostname: `127.0.0.1` и `localhost` имеют разные cookie. Основной адрес — `127.0.0.1`.

## Каждый следующий запуск

```bash
cd /Users/maria/Desktop/afterlight
pnpm local:start
pnpm dev
```

Повторный `local:start` безопасен: статьи с существующими ID не перезаписываются и не дублируются. Он не пересоздаёт владельца. Явная повторная проверка seed: `pnpm local:seed`.

Остановка:

1. В терминале приложения нажмите **Ctrl+C**.
2. Остановите только основные сервисы AFTERLIGHT:

```bash
pnpm local:stop
```

База и загруженные обложки сохраняются в Docker volumes. Не удаляйте эти volumes через Docker Desktop. Наличие файлов исходного кода не заменяет резервную копию пользовательских данных.

Состояние и перезапуск:

```bash
pnpm local:status
pnpm local:restart
```

`local:restart` сохраняет volumes. Приложение может показать временную недоступность базы во время перезапуска; после готовности обновите страницу. После изменения `.env.local` перезапустите `pnpm dev`.

## Production-режим на этом компьютере

```bash
pnpm local:start
pnpm build
pnpm start
```

Перед `pnpm start` остановите `pnpm dev`, поскольку обе команды используют порт 3300. Это обычные `next dev`, `next build` и `next start`. Для dev/build выбран официальный режим `--webpack`: внутренний процесс Turbopack в этой среде завершается ошибкой открытия служебного порта. Production-сервер запускается штатным `next start`.

## Работа редактора

Войдите через `/login` → создайте статью → заполните вкладки RU и EN → загрузите обложку → сохраните черновик или опубликуйте.

- Черновик допускает незаполненный перевод. Публикация требует заполненные обе версии и обложку.
- Перевод вводится вручную. Переключатель языка статьи сохраняет её адрес.
- Список передаёт только метаданные; полный материал загружается отдельным защищённым запросом. Есть пагинация.
- Одновременное сохранение одной версии даёт конфликт `409`; второй запрос не затирает текст.
- Адрес статьи после первого сохранения не меняется.
- Загрузка: **JPEG, PNG или WebP до 4 MiB**. Лимит снижен с исходных 5 MiB. Сервер проверяет фактические байты, MIME, полное декодирование и размерность (до 40 млн пикселей), применяет ориентацию, ограничивает сторону 4096 px, удаляет метаданные и сохраняет нормализованный WebP.
- Обложки лежат в private bucket `covers`. Прямые загрузки и выдача signed URL из браузера закрыты. `/media/[key]` каждый раз проверяет право владельца или наличие опубликованной ссылки и возвращает `no-store`.
- Снятие с публикации закрывает **новые** запросы к статье и её непубличной обложке. Уже скачанную читателем копию отозвать невозможно. Если одна обложка используется другой опубликованной статьёй, она остаётся доступной.
- Выход выполняется POST-запросом, удаляет cookie и отзывает сессии пользователя. Права владельца в БД дополнительно зависят от существующей записи Auth-сессии. Завершённые ответы/скачанные файлы выход не отменяет.

## Восстановление доступа владельца

При работающих локальных сервисах:

```bash
pnpm local:owner --reset-password
```

Команда меняет пароль только у уже назначенного владельца после ввода его email; ввод пароля скрыт. Это локальная административная команда для человека с доступом к компьютеру и `.env.local`, не публичный endpoint. Храните доступ к компьютеру и файлу конфигурации под своим контролем.

## Настройки

`.env.example` документирует все переменные; `.env.local` генерируется автоматически и исключён из Git.

| Переменная | Назначение |
| --- | --- |
| `SITE_ORIGIN` | Канонический адрес сайта, по умолчанию `http://127.0.0.1:3300` |
| `ALLOWED_ORIGINS` | Точный список разрешённых Origin для POST, разделённый запятыми |
| `SUPABASE_URL` | URL локального Supabase API |
| `SUPABASE_PUBLISHABLE_KEY` | Облачный Publishable key для серверного клиента с правами текущей сессии и RLS |
| `SUPABASE_SECRET_KEY` | Облачный серверный ключ: назначение владельца, проверенная загрузка и выдача медиа, лимит попыток входа |
| `SUPABASE_ANON_KEY` | Совместимое имя для локального legacy anon key |
| `SUPABASE_SERVICE_ROLE_KEY` | Совместимое имя для локального legacy service-role key |

Секретный ключ не используется в `NEXT_PUBLIC_*` и не отправляется браузеру. Произвольные `Host`, `oai-authenticated-*`, email или client state не назначают владельца. Проверка сессии выполняется через Supabase Auth `getUser`, права — через `is_owner` и RLS. Изменения требуют разрешённый Origin; вход дополнительно ограничивается счётчиком в PostgreSQL.

В облаке задавайте новые имена ключей, в локальном `.env.local` оставьте созданные CLI прежние имена. Разные значения одновременно под новым и совместимым именем вызывают ошибку, чтобы не смешать проекты. Переменные `NEXT_PUBLIC_SUPABASE_*` этому приложению не нужны: клиент Supabase здесь работает на сервере.

## Проверки

```bash
pnpm typecheck
pnpm lint
pnpm test:unit
pnpm build
pnpm test:sql
pnpm test:integration
```

Для браузерной проверки при первом запуске может потребоваться:

```bash
pnpm exec playwright install chromium
```

`test:sql` и `test:integration` создают отдельное окружение `afterlight-test` в `work/test-services`, используют те же миграции, реальные Auth/PostgreSQL/Storage и случайно сгенерированные технические аккаунты. Они не назначают владельца основной базы и не изменяют её материалы. Пароли технических пользователей живут только в памяти процесса. Интеграционный тест запускает production-сборку на порту 3400; поэтому сначала нужен `pnpm build`.

Проверяются запреты для гостя/другого пользователя/поддельных заголовков, RLS и прямой API, атомарное сохранение, лимиты обложек, RU/EN, публикация, снятие с публикации, настоящий браузерный редактор, выход и сохранность статей/файлов после stop/start без удаления volumes. Результат и скриншоты: `outputs/integration/` (исключены из Git). Отдельные SQL-тесты используют транзакцию с rollback.

После проверок остановите только тестовые сервисы:

```bash
pnpm local:test:stop
```

Фактически выполненные проверки и оставшееся первичное действие владельца перечислены в [локальном отчёте](docs/LOCAL_VERIFICATION.md). Полный перечень файлов — [CHANGED_FILES.md](docs/CHANGED_FILES.md).

## Границы этой работы

Подготовлено подключение указанного владельцем облачного Supabase. Проверены публичный API и Publishable key; применение облачных миграций, создание владельца и публикация требуют следующих шагов из [DEPLOYMENT.md](docs/DEPLOYMENT.md). Vercel, удалённый Git и прежний размещённый сайт не изменялись. Рабочие материалы прежнего хостинга отсутствуют в этой копии. Локальный seed не перезаписывает пользовательские изменения; в облаке seed автоматически не запускается.
